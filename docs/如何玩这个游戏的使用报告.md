# 如何玩这个游戏的使用报告

## 1. 游戏与参与方式

电波接力（Turing Signal Relay）是一款双阵营AI策略竞赛游戏。双方通过移动、报文运输、通信组网、器材建设、压制与枢纽任务获得分数。每方拥有3名通信员、2名工兵和2名运输员。

单位只接受AI程序的指令。选手编写C++17策略并提交ai.cpp，裁判服务器推进规则，Unity客户端负责观察比赛和播放回放。鼠标用于查看地图、选中单位和操作播放界面。

本报告依据当前源码与实际构建入口编写。规则版本为signal-relay-1.0，完整模式为relay-full-v1，AI协议为2。当前交付包位于开发电脑的artifacts/stage7/release-final，构建源码提交为01b22ce。

| 身份 | 需要准备的内容 | 可进行的操作 |
| --- | --- | --- |
| 观众 | Windows客户端、回放文件或授权观战地址 | 查看单位、迷雾、得分、事件与完整回放 |
| 选手 | 裁判分配的队伍账号、ai.cpp | 上传版本、查看编译结果、下载本队可见结果与日志 |
| 裁判 | 裁判账号与已运行的平台 | 创建队伍账号、安排双局、查看结果和生成观战令牌 |
| 开发者 | 源码、.NET10、C++17工具链及Unity Editor | 运行可信样例、修改策略、构建和回归验证 |

## 2. 最快体验一场比赛

### 2.1 准备客户端

取得TuringSignalRelay-windows.zip，完整解压到一个新目录。保留TuringSignalRelay.exe旁的Data目录、UnityPlayer.dll和其他配套文件，在该目录运行TuringSignalRelay.exe。

安装包中的examples包含game-1.replay.json和game-2.replay.json。这是两支样例AI进行双局换边产生的完整回放，每局9000 tick。客户端启动后首先加载内置演示数据，手动打开examples中的文件即可查看完整样例比赛。

### 2.2 打开完整回放

1. 在右侧面板滚动到“回放文件路径 (.json / .jsonl)”。
2. 填入解压目录中game-1.replay.json的完整路径。
3. 点击“打开回放”，确认状态显示Replay loaded，时间轴更新。
4. 点击“播放”。需要逐帧观察时先暂停，再点击“单步”。
5. 第一局看完后，用相同方式打开game-2.replay.json。

如果解压位置是C:\Games\TuringSignalRelay，路径输入框中填写以下内容。路径文本包含文件名，使用Windows“复制为路径”时去掉外层双引号。

```text
C:\Games\TuringSignalRelay\examples\game-1.replay.json
```

### 2.3 操作界面

| 控件或操作 | 用法 |
| --- | --- |
| 播放、暂停 | 控制离线回放的播放状态 |
| 单步 | 离线模式下推进一帧 |
| 0.5x、1x、2x、4x | 调整离线回放速度 |
| 时间轴 | 在离线回放中跳转到指定帧 |
| 全图、红方视角、蓝方视角 | 查看完整地图或按对应阵营的可见性过滤 |
| 点击单位或设施 | 查看编号、位置和状态，单位视野圆随选中显示 |
| 鼠标拖动地图、滚轮 | 平移与缩放镜头 |
| 重置镜头 | 恢复地图镜头 |
| 跟随选中单位、跟随事件 | 切换镜头跟随方式 |
| 小地图 | 点击定位主地图视野 |
| 侧栏滚轮 | 查看回放路径、观战设置、得分曲线及事件记录 |

每秒10 tick，每局9000 tick，对应15分钟规则时间。服务器可以加速推进模拟，客户端按所选倍率播放已保存的帧。

## 3. 游戏目标与计分

### 3.1 地图和单位

地图为96×96格，采用180°旋转对称。坐标从左下角开始，x、y范围均为0—95。双方各有指挥所、三处前沿报点和两处兵站，中央有公共资源与2×2枢纽区域。

| 单位 | 每方数量 | 可携带内容 | 主要用途 |
| --- | --- | --- | --- |
| 通信员 | 3 | 1份报文 | 架台、组网、译电、压制和送报 |
| 工兵 | 2 | 最多3份器材 | 架桥和建设固定中继 |
| 运输员 | 2 | 最多6份器材或3份报文 | 大容量运输、转交及枢纽交付 |

普通格存在占用和移动预留，桥渡口使用队列。道路、草地和特殊过河通道会影响耗时。AI根据实际状态规划路线，受限敌方信息只在本方视野内出现。

### 3.2 任务与分数

| 项目 | 得分规则 |
| --- | --- |
| 平报 | 生成后600 tick内交付15分，601—900 tick交付10分，再晚5分 |
| 急报 | 同一公共任务双方各有一次资格，先到45分，后到20分，同tick首次到达双方均得45分 |
| 密报 | 先完成连续50 tick译电，900 tick内交付37.5分，901—1200 tick为25分，再晚12.5分 |
| 通播 | 两个指定报点同时保持有效连通覆盖30 tick，完成后20分 |
| 总攻令 | 时限300 tick，先到60分，后到20分，同tick首次到达双方均得60分 |
| 建造桥 | 完成建设得20分，每方前3座计建设分 |
| 固定中继 | 完成建设得15分，每方前4座计建设分 |
| 枢纽 | 终局人数、有效网络覆盖、累计交付器材三个条件分别40分 |
| 器材结余 | 按己方携带与指挥所库存结算，每份1分，最多10分 |

枢纽人数要求终局至少3名本方单位位于区域内，器材条件要求累计交付至少6份。9分钟后可在枢纽交器材。己方兵站和中央公共器材允许取用，敌方兵站的器材归属受限。

通信员架台耗时20 tick。工兵架桥耗时60 tick并消耗3份器材，建中继耗时50 tick并消耗2份器材。压制持续40 tick，施术通信员冷却250 tick。天气会改变通信覆盖，天气结束后恢复基础覆盖。完整参数以[批准规则](RULE_DECISIONS.md)为准。

### 3.3 双局胜负

一场比赛包括同地图、同种子的两局，第二局交换阵营。正常情况下依次比较双局总分、单局最高分、急报与总攻令送达次数，全部相同记平局。

单方选手故障按整场判负处理，双方均故障时双方均无获胜资格。原始得分与部分回放仍保留，结果中的winnerTeam表示队伍编号，具体阵营映射记录在每局teamBySide中。

## 4. 编写并提交自己的AI

### 4.1 从样例开始

SDK包中包含turing_sdk.hpp、两个完整样例、示例辅助头文件及固定JSON依赖。首次参赛可将sdk/cpp/examples/courier.cpp复制为ai.cpp，再用队伍账号上传。正式服务器已提供相同SDK和示例包含路径。

最小合法策略如下。它每帧提交一个空动作列表，可用于验证协议接通。

```cpp
#include "turing_sdk.hpp"

int main() {
    tsr::Client ai;
    while (ai.getframeinfo()) {
        ai.submit();
    }
}
```

在getframeinfo返回true的循环中读取ai.frame()，计算动作并调用moveTo、loadMsg、deliverMsg等方法，帧末调用一次submit。初始化的side由SDK读取，单位ID为side×100加单位序号，0—2为通信员、3—4为工兵、5—6为运输员。

帧0的命令在tick1生效。每个单位每tick只取首条指令，然后验证合法性。调试信息写入stderr。stdout承担JSON Lines协议输出。

### 4.2 本地运行可信样例

Windows需要Visual Studio C++17 x64工具链及.NET10 SDK。在源码仓库根目录运行，输出目录选择新名字。

```powershell
./tools/check-local-match.ps1 -Dotnet 'D:\kanfe\dotnet10\dotnet.exe' -OutputDirectory "$PWD/artifacts/my-first-match"
```

看到LOCAL_MATCH_CHECKS_PASSED后，在输出目录的series/game-1和game-2中查找relay.replay.json，再通过客户端“打开回放”查看。这个流程同时运行规则和故障回归，适合开发环境验证。

完整SDK接口和单独编译方式见[SDK说明](../sdk/cpp/README.md)。

### 4.3 连接平台

由裁判提供服务器地址和队伍账号。在本机建立SSH隧道并保持终端运行，然后打开http://127.0.0.1:5188/Login。

```text
ssh -N -L 5188:127.0.0.1:5188 ubuntu@YOUR_SERVER
```

使用选手账号登录，在“提交AI”页面选择UTF-8编码的ai.cpp，填写可选版本说明并提交。源码上限256 KiB，每队最多同时保留5个待编译任务。

“提交历史”依次显示等待编译、正在编译、可参加比赛或编译失败。编译成功后由裁判选择两支不同队伍的就绪提交发起比赛。账号由裁判统一创建，同队账号共享本队提交和比赛记录。

## 5. 查看结果与在线观战

在“比赛结果”打开对应比赛，检查队伍名称、两局得分、总分、胜负依据和故障原因。下载JSON结果与两局回放，本方运行日志按队伍归属授权。

在线观战操作如下。

1. 在结果页点击“生成观战令牌”。
2. 复制快照URL，在Unity侧栏“观战快照地址”中粘贴。
3. 复制令牌，在“访问令牌”中粘贴，点击“连接观战”。
4. 第二局在快照URL后添加?game=2，重新连接。
5. 在线模式使用“暂停显示”和“回到实时”，离线时间轴与单步在断开在线连接后使用。

令牌有效期一小时，只授权该场快照。通过SSH隧道使用本机回环URL。界面中的令牌输入采用掩码显示，观战令牌和账号密码由持有人保管。

## 6. 资源限制与故障处理

| 约束 | 正式值 |
| --- | --- |
| 每方每tick | 10ms CPU，100ms墙钟兜底 |
| 初始化 | 2秒 |
| 运行内存与进程 | 256 MiB，1个进程，零交换配额 |
| 编译 | 30秒，512 MiB |
| 输入与动作 | 每帧输入2 MiB，输出单行64 KiB，最多128动作 |
| 诊断 | stderr累计保留最多1 MiB |

累计三次计算超时会判整场负。畸形JSON、错误协议、未来tick、动作超限、进程崩溃、内存越限及文件/网络/进程/线程违规会形成选手故障。基础设施中断最多自动重试一次，仍失败时由裁判处理。

## 7. 常见问题

| 现象 | 检查与处理 |
| --- | --- |
| 打开回放失败 | 检查完整文件路径、外层引号及JSON文件完整性，查看状态栏错误 |
| 侧栏找不到输入框 | 在右侧面板滚动，回放和在线设置位于单位信息下方 |
| 在线401 | 重新生成有效令牌，检查比赛URL和SSH隧道 |
| 只有内置演示 | 打开examples中的完整回放，或连接授权快照 |
| 编译失败 | 查看提交历史的诊断，检查C++17、文件名与包含路径 |
| 结果显示选手故障 | 查看故障原因、本方日志和部分回放，修复策略后提交新版本 |
| 已登录但无法发起比赛 | 发起比赛由裁判账号执行 |
| 服务器刚启动时连接失败 | 等待health接口返回200，确认两个项目服务active后重试 |
