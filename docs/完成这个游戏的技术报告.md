# 完成这个游戏的技术报告

2026-11-07后续发布采用Unity6000.6.8f1作为统一工程与构建版本，用户已取消原6000.3.26f1限制。公网接入采用Nginx HTTP反向代理，应用继续监听127.0.0.1:5188，公开交付文件独立位于/srv/tsr/downloads。以下原版工具链与独立副本结果保留为历史证据，当前状态以README发布记录为准。

## 1. 项目目标与当前成果

电波接力是面向AI策略竞赛的双阵营比赛系统。开发范围包含权威规则、地图移动、C++策略协议、Unity二维观战与回放、账号提交平台、隔离编译执行和Ubuntu运维。原五人职责当前由用户个人承担，编号用于定位模块。

现有完整模式relay-full-v1使用协议2，规则signal-relay-1.0绑定R01—R18批准文档和R19补充摘要。工程保留早期Bootstrap与平报子集供兼容回归。实际实现与验收完成度分别记录。

最新交付代码基点为01b22ce，公开源码、SDK、Windows客户端、Linux原生裁判、Linux正式服务已形成5份包。项目使用C#与Unity实现规则和画面，选手程序通过C++17 SDK接入。

生产Worker通过Evaluation.csproj直接编译引用Unity工程的纯C#源码，用户已确认采用此宿主。Unity Linux原生裁判保留为跨宿主一致性验证入口。Web请求将任务写入数据库，独立Worker推进比赛。

一场比赛的数据链如下。

```text
队伍账号上传ai.cpp
    → 源码摘要与持久化提交
    → nsjail隔离编译和只读二进制缓存
    → Worker领取比赛并为两方准备独立沙箱
    → 可见帧经stdin进入C++策略，动作经stdout返回
    → 同一C#规则核心推进tick
    → 双局结果、动作回放、快照和诊断落盘
    → 平台按身份提供下载，Unity显示回放或授权快照
```

## 3. 确定性状态与运行顺序

规则使用整数tick、格坐标、器材数量及整数半分。10 tick对应1秒，9000次推进形成终局帧9000。帧n的命令在n+1应用，每单位每tick取首条命令后检查合法性。

规则组合依次处理命令及撤台、天气与刷新、任务完成和移动、视野及通信图、译电/通播与交付、超期及计分、快照与摘要。终局额外结算枢纽和器材结余。界面播放速度独立于裁判tick。

随机事件由种子与事件序号确定，双方报点与事件旋转配对。AI行为不消耗事件随机序列。完整摘要覆盖新增状态，回放记录有效命令及逐tick摘要，重演时验证状态一致性。

主要入口为RelayMatchEngine、RelayFullStateHash、RelayReplay和RelaySeries。双局聚合校验规则、地图和种子，记录阵营到队伍的映射，再计算胜负与故障结果。

## 4. 地图、移动与信息过滤

地图采用96×96固定公开模板，地形、站点与跨河点180°对称。寻路使用纯C#整数格网A*，按地形、角色和专用通道计算耗时。同价路径采用稳定顺序并与阵营旋转对应。

移动期间预留目标格，普通格禁止迎面交换；争抢按tick轮换阵营优先，同阵营按稳定单位ID处理。连续阻挡后重新寻路。铁索桥、渡口和建造桥维护通行队列，运输员过河耗时翻倍。

AI观察由权威状态单独生成，公开静态地图、时间表、本方状态和双方分数。敌方单位、建筑及可变资源按当前视野过滤，本方内部寻路数组经过清理。Unity全图快照和AI观察分别生成。

## 5. 完整玩法与边界修复

RadioNetwork根据双方节点半径的较小值构图，使用BFS判断至指挥所的连通性。FullMessageSystem处理五类任务、载运、站点缓存、译电、通播和交付。FullRuleSystem处理材料归属、预留退款、施工、压制、天气、补偿及终局条件。

R19限制器材取用范围为己方兵站和中央公共资源。施工预留计入携带容量，完成才计建设分，中断全额退回。密报需要连续50 tick译电，通播需要连续30 tick双目标覆盖。进度条件中断后按批准规则重置。

本轮发现并修复了台站缓存持有关系问题。原逻辑查找持有节点时过滤inactive节点，使受压制缓存重新进入地面收集；未连通节点的缓存也可能被较大覆盖半径的其他节点绕过链路转发。修复后，存在的持有节点保留缓存，只有有效且已连通时才发送。先添加失败回归，再修复并验证。

完整规则检查扩展为76项，包含台站缓存、整局任务数量、种子配对、通播不同目标、库存上限以及真实规则函数构成的附录668分账。样例完整对局的原有摘要保持一致。

## 6. AI协议与计算预算

每方使用长期进程。SDK首先接收relay-init并回复relay-ready，再逐帧读取relay-frame，输出一行relay-commands并flush。一个tick的动作集中于actions列表，桥接器检查版本、阵营、tick、JSON结构、动作数和字节上限。

AiProcessBridge管理受控管道、限长UTF-8读取、诊断截断、迟到帧、取消及进程回收。RelayAiSession统一握手、双侧请求、超时累计和正常/故障回放。正式运行通过沙箱工厂和停止回调接入同一会话实现。

| 项目 | 预算 |
| --- | --- |
| 源码 | UTF-8，最多256 KiB |
| 编译 | 30秒、512 MiB、最多64进程、单文件16 MiB |
| 运行 | 每方256 MiB、1进程、零交换配额 |
| tick | 每方合计10ms CPU及100ms墙钟 |
| 初始化 | 每方2秒 |
| 协议 | 输入2 MiB，stdout单行64 KiB、最多128动作 |
| 日志 | stderr累计保留最多1 MiB |

正式CPU统计读取AI cgroup的usage_usec，内存统计读取memory.peak。累计三次超时形成整场故障判负，其他协议和隔离违规直接记录选手故障。基础设施异常按整场最多重试一次处理。

## 7. 正式隔离实现

运行程序限定为静态x86_64 ELF。Root拥有的固定协议helper管理编译、准备、运行、停止、审计和释放。Worker通过限定sudoers条目调用helper，参数ID经过格式校验，源码和产物绑定摘要。

nsjail为编译和运行采用分别维护的seccomp策略。运行使用只读根文件系统、独立命名空间、低权限身份与cgroup。业务文件打开、网络、线程和子进程由策略拒绝；运行库初始化所需调用列于策略中。编译器在独立工作目录内运行，具备自身资源约束。

编译缓存采用临时目录准备并发布只读产物，记录源码、二进制、SDK及策略摘要。资源回收通过cgroup.kill、监督器回收、cgroup和私有目录删除完成。

Worker启动回收改为扫描Root管理的runs目录，覆盖预备沙箱已经创建、启动脚本尚未写入的中断窗口。先构造遗留状态复现问题，再使用重启和SIGKILL测试验证回收及第二次尝试。

内存样例按4 MiB逐次分配并逐页写入，实测驻留峰值265199616字节，约252.9 MiB，随后分配失败退出86。该次记录中oom_kill为0，测试同时核对256 MiB内存、零交换和单进程限制。

## 8. 平台、数据与授权

Identity负责密码哈希、角色、会话及锁定。裁判创建队伍账号；TeamId将用户与提交关联。写操作使用防伪令牌，查询和下载检查队伍归属或裁判角色。比赛请求使用requestKey实现幂等，相同key的冲突参数被拒绝。

SQLite保存用户、队伍、提交、比赛和产物索引。提交采用事务限制同队最多5个待编译任务，文件存储在受控GUID目录。任务状态、尝试次数、结果目录与产物摘要持久化。队列使用单实例Worker串行消费。

比赛快照采用协议1的ObserverSnapshotResponse，包含tick、status和snapshot。相关队伍或裁判可取得一小时有效的比赛专属只读令牌。源代码、结果、回放和两方日志分别按接口归属验证。

EF Core迁移支持新库及此前相同初始结构库，升级前核对结构。备份使用SQLite快照及逐文件摘要，恢复目标要求新目录。平台和Worker通过专用组共享数据库，主库及WAL/SHM权限为0660，数据目录2770，密钥目录0700。

## 9. Unity显示与自有素材迁移

观战界面使用运行时uGUI，读取只读ObserverFrame。地图、迷雾、裁剪、单位选中、视野圆、小地图、镜头跟随、得分曲线和事件日志统一消费快照。

离线支持播放、单步、倍速与跳转。在线使用UnityWebRequest携带Bearer令牌，校验快照版本和tick，过滤重复或旧帧，并处理超时、取消、连接切换及令牌错误。

旧工程迁入了36段范围圆算法和限长日志，分别修复闭环、裁剪、tick时间和来源切换。13张自有模型派生精灵进入公开源码。原始模型及完整旧工程保留在本机，用户已确认代码与素材所有权。来源与摘要见[复用记录](REUSE.md)。

## 10. 发布、部署与跨宿主验证

Windows用于C#/Unity与C++开发，Ubuntu24.04 x86_64用于正式隔离评测。.NET10的Platform、Worker与共享Evaluation独立于Unity Editor运行，Unity脚本维持其支持的C#与API范围。

发布流程生成Windows观战包、Linux原生裁判包、Linux正式服务包、SDK包及源码快照。BUILD-INFO记录源码提交、修改状态和Editor版本，source-manifest记录源码摘要，DELIVERY记录各归档字节数及SHA256。校验同时覆盖PE/ELF架构、归档CRC、路径与脚本换行。

systemd维护tsr-platform与tsr-worker，服务使用专用账号，Web监听127.0.0.1:5188，通过SSH隧道访问。多版本目录与current软链接用于更新和回退。当前发布目录和DLL摘要以最新验收记录为准。
